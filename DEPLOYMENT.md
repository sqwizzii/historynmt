# Розгортання: Vercel + Render + Neon

Схема: **браузер → Vercel** (React) **→ Render** (Spring Boot API) **→ Neon** (PostgreSQL).
Адреси в цій інструкції це плейсхолдери: `<...>` замініть своїми, коли сервіси створені.
Жодних секретів у Git не записуйте: усі значення вводяться лише в панелях Render, Vercel і Neon.

## Обмеження безкоштовних тарифів (за офіційною документацією на дату підготовки)

- **Render, Free web service** ([render.com/docs/free](https://render.com/docs/free)): сервіс «засинає» після 15 хвилин без запитів, пробудження займає близько хвилини; файлова система тимчасова (у проєкті зображення зберігаються в БД, тож це не проблема); 750 безкоштовних годин на місяць; Render прямо не рекомендує Free для production.
- **Neon, Free plan** ([neon.com/docs/introduction/plans](https://neon.com/docs/introduction/plans)): 1 ГБ сховища на проєкт, 100 CU-годин на місяць, обчислення вимикається після 5 хвилин простою (перший запит після паузи повільніший), вікно відновлення історії лише 6 годин. Зображення питань і карток лежать у БД, тому 1 ГБ може закінчитися.
- **Vercel**: актуальні ліміти та умови (зокрема щодо комерційного використання Hobby) перевірте на [vercel.com/pricing](https://vercel.com/pricing); я їх не перевіряв.
- Для довгострокового зберігання даних безкоштовний варіант годиться для тестування й невеликих пілотів. Для реальної роботи з учнями плануйте платні плани й регулярні резервні копії (див. розділ 10).
- Не використовуйте безкоштовну БД Render Postgres: вона видаляється через 30 днів і не має резервних копій.

## 1. База даних у Neon

1. Зареєструйтеся на [neon.com](https://neon.com), створіть **Project** (регіон ближчий до Render, наприклад Frankfurt).
2. Відкрийте **Connect**, оберіть бази `neondb` і роль, **вимкніть перемикач «Connection pooling»** (потрібен прямий хост без `-pooler`: Flyway використовує advisory-блокування, які не працюють через pooler у транзакційному режимі).
3. Скопіюйте рядок підключення виду `postgresql://<user>:<password>@<host>/<db>?sslmode=require`. З нього складіть три значення для Render:
   - `DB_URL` = `jdbc:postgresql://<host>/<db>?sslmode=require` (без користувача й пароля, без `channel_binding`);
   - `DB_USERNAME` = `<user>`;
   - `DB_PASSWORD` = `<password>`.
4. Нічого створювати вручну не потрібно: міграції Flyway (V1–V13) створять схему в порожній базі при першому запуску бекенду. Локально це перевірено на порожній PostgreSQL з профілем `prod`.

## 2. Бекенд у Render

1. На [render.com](https://render.com) натисніть **New → Web Service**, підключіть GitHub-репозиторій `sqwizzii/historynmt`.
2. Налаштування:
   - **Runtime**: Docker (використовується `Dockerfile` у корені; профіль `prod` у ньому вже заданий);
   - **Root Directory**: порожньо; **Branch**: `main`;
   - **Instance Type**: Free (для тесту);
   - **Health Check Path**: `/api/health` (публічний, не звертається до БД, тому не будить Neon).
3. **Environment Variables** (Render сам задає `PORT`, бекенд його підхоплює):

| Змінна | Значення / де взяти |
|---|---|
| `DB_URL` | JDBC-адреса з кроку 1.3 |
| `DB_USERNAME`, `DB_PASSWORD` | з Neon, крок 1.3 |
| `JWT_SECRET` | згенеруйте: `openssl rand -base64 48` (на Windows: `[Convert]::ToBase64String((1..48 \| % {Get-Random -Max 256}))`) |
| `CORS_ALLOWED_ORIGINS` | адреса фронтенду без `/` наприкінці, напр. `https://<проєкт>.vercel.app` (на першому деплої поставте тимчасово будь-яку https-адресу, виправте у розділі 5) |
| `ADMIN_USERNAME` | логін адміністратора (не `admin`, обирайте власний) |
| `ADMIN_PASSWORD` | пароль від 12 символів (див. розділ 6) |

   Не задавайте `BOOTSTRAP_TEACHER_*`, `LEGACY_*`: у новій порожній базі вони не потрібні, а демо-акаунти в профілі `prod` не створюються.
4. Натисніть **Create Web Service**. Перша збірка триває кілька хвилин. Публічна адреса бекенду матиме вигляд `https://<сервіс>.onrender.com`.

## 3. Фронтенд у Vercel

1. На [vercel.com](https://vercel.com) натисніть **Add New → Project**, імпортуйте той самий репозиторій.
2. Налаштування:
   - **Root Directory**: `frontend`;
   - **Framework Preset**: Vite (збірка `npm run build`, каталог результату `dist` визначаються автоматично);
   - **Environment Variables**: `VITE_API_URL` = `https://<сервіс>.onrender.com/api` (з `/api` наприкінці). Це змінна збірки, секретів у ній немає. Адресу БД у фронтенд не передавайте.
3. Натисніть **Deploy**. Файл `frontend/vercel.json` вже містить перенаправлення на `index.html`, тож прямі посилання (`/teacher/tests`) працюють.
4. Якщо змінюєте `VITE_API_URL`, зробіть **Redeploy**: змінна вбудовується під час збірки.

## 4. Адреса бекенду у Vercel

Це пункт 3.2: `VITE_API_URL`. Перевірка: відкрийте сайт, у DevTools → Network запити мають іти на `https://<сервіс>.onrender.com/api/...`, а не на `localhost`.

## 5. CORS після отримання домену Vercel

1. Скопіюйте остаточну адресу сайту (напр. `https://<проєкт>.vercel.app` або власний домен).
2. Render → ваш сервіс → **Environment** → `CORS_ALLOWED_ORIGINS` = ця адреса без `/` наприкінці. Кілька адрес розділяйте комою (напр. основний домен і `www`).
3. Збережіть: Render перезапустить сервіс. Прев'ю-адреси Vercel (`*-git-*.vercel.app`) не дозволені, доки ви їх не додасте явно.
4. Перевірка: вхід на сайті проходить; запит з іншого домену отримує 403 на preflight.

## 6. Безпечне створення production-адміністратора

- Адміністратор створюється при старті бекенду з `ADMIN_USERNAME` і `ADMIN_PASSWORD` (див. Render → Environment). Створення ідемпотентне: наявному користувачеві роль і пароль не змінюються.
- Пароль вводьте лише в панелі Render; не надсилайте його в чатах і не зберігайте в репозиторії. У логах він не з'являється.
- Після першого входу змініть пароль на сторінці акаунта й **видаліть змінну `ADMIN_PASSWORD`** з Render: при наступних запусках вона не потрібна.
- Роль ADMIN неможливо отримати через реєстрацію; нових адмінів призначає лише діючий адмін у розділі «Користувачі».

## 7. Перевірка міграцій Flyway

1. Render → **Logs**: мають бути рядки `Successfully applied 13 migrations ... now at version v13` і `Started NmtHistoryApplication`.
2. Neon → **SQL Editor**, лише читання: `SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;`. Усі `success = true`, остання версія 13.
3. Якщо міграція впала, сервіс не стартує: прочитайте помилку в логах. Нічого не видаляйте в базі й не перезапускайте повторно без аналізу.

## 8. Перевірка функцій (на реальних адресах)

1. `https://<сервіс>.onrender.com/api/health` повертає `{"status":"UP"}` (перший запит після простою може йти ~1 хвилину).
2. Вхід адміністратора: сторінка «Увійти» → `ADMIN_USERNAME` / пароль → «Огляд платформи».
3. Реєстрація вчителя: у приватному вікні «Для вчителів» → створити акаунт. До активації підписки створення тестів недоступне (повідомлення про підписку).
4. Адмін → «Користувачі» → вчитель → «Активувати» (місячний або річний план) → вчитель створює тест із питанням.
5. Вчитель → «Учні та результати» → скопіювати код запрошення → у ще одному вікні зареєструвати учня за цим кодом (`/register`).
6. Вчитель відкриває тест → «Призначити учням» → обирає учня. Учень бачить тест; інший учень (без призначення) його не бачить.
7. Учень проходить тест → бачить результат; вчитель бачить результат у розділі «Учні та результати».
8. Права доступу: другий вчитель не бачить тестів і учнів першого; учень і вчитель не мають доступу до `/admin`; вчитель не може змінити системний тест.

## 9. Перевірка збереження даних після перезапуску

1. Створіть тест і результат (розділ 8).
2. Render → сервіс → **Manual Deploy → Restart service** (або дочекайтеся «засинання» та пробудження).
3. Після запуску ті самі дані мають бути на місці: вони лежать у Neon, а не на диску Render. Після простою Neon (5 хв) перший запит до БД може бути повільним.

## 10. Резервні копії

Безкоштовний Neon зберігає історію лише 6 годин, тому робіть копії самі (потрібен клієнт PostgreSQL):

```bash
pg_dump "postgresql://<user>:<password>@<host>/<db>?sslmode=require" -Fc -f backup_$(date +%F).dump
```

Зберігайте файл поза репозиторієм (каталог `backups/` та `*.dump` ігноруються Git). Відновлення: `pg_restore -d "<нова база>" --no-owner backup.dump`.

## Локальний запуск не змінився

Локально бекенд і фронтенд запускаються як у `README.md`; `docker-compose.yml` (власний сервер із Caddy) теж працює без змін. Профіль `prod` у Docker-образі увімкнено за замовчуванням, тому локально запускайте бекенд через `./mvnw spring-boot:run`, а не через цей образ.
