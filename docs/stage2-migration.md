# Етап 2: міграція до моделі власності матеріалів

Міграції V11 і V12 лише **додають** таблиці й колонки (`subjects`, `subscriptions`, `owner_id`, `subject_id`, `grade`,
`scoring_scale`, `teacher_id`, `legacy_free_access`) та розширюють обмеження ролі значенням `ADMIN`. Жодні користувачі, тести,
питання, варіанти, картки, результати (разом із `nmt_score`), спроби й історія практики не видаляються й не змінюються.

Хто є власником старих даних, **вирішує лише конфігурація**, а не припущення. Це робить `LegacyOwnershipInitializer`
під час першого запуску нової версії.

## Змінні середовища

| Змінна | Призначення |
|---|---|
| `LEGACY_TEACHER_USERNAME` | Логін **існуючого** користувача з роллю `TEACHER`, якому належать усі наявні тести, модулі карток і учні. Обов'язкова при першому запуску на БД із даними. Не припускайте, що це `teacher`. |
| `LEGACY_ASSIGN_ALL_STUDENTS` | `true` лише якщо в БД кілька вчителів і ви підтверджуєте прив'язку всіх неприв'язаних учнів до `LEGACY_TEACHER_USERNAME`. |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Окремий акаунт адміністратора платформи. Пароль (від 12 символів) задається лише тут або в сховищі секретів, ніколи в коді чи репозиторії; у логи не потрапляє. Створення ідемпотентне. |
| `ADMIN_PROMOTE_EXISTING` | `true` дозволяє підвищити до ADMIN **наявного учня** з логіном `ADMIN_USERNAME`. Вчителів і наявних адміністраторів не чіпає. За замовчуванням `false`: роль наявного користувача не змінюється. |
| `IMAGE_URL_TTL_MINUTES` | Строк дії підписаних посилань на зображення приватних матеріалів (за замовчуванням 360). |

Профіль `prod` запускається з `app.legacy.strict=true`: якщо є матеріали чи учні без власника, а конфігурація недостатня
(немає `LEGACY_TEACHER_USERNAME`, користувача немає або він не `TEACHER`, або вчителів кілька без `LEGACY_ASSIGN_ALL_STUDENTS`),
застосунок **не стартує** і друкує діагностику: список вчителів, кількість тестів, модулів і неприв'язаних учнів.
Після успішного призначення в `app_settings` ставиться позначка `legacy_ownership_done`, тож крок більше не виконується, а системні
матеріали адміністратора ніколи не передаються вчителю.

## Порядок оновлення на сервері

1. **Резервна копія** і перевірка відновлення (обов'язково до оновлення):

   ```bash
   docker compose exec -T db pg_dump -U nmt -Fc nmt_history_db > backups/pre_stage2.dump
   # перевірка відновлення у тимчасову базу, не в робочу
   docker compose exec -T db createdb -U nmt nmt_restore_check
   docker compose exec -T db pg_restore -U nmt -d nmt_restore_check --no-owner < backups/pre_stage2.dump
   ```

   Порівняйте відбиток `scripts/db-fingerprint.sh` робочої бази й відновленої: кількість рядків і хеші мають збігтися
   (скрипт підключається через `psql`; у Docker запустіть його з хоста з прокинутим портом або через `docker compose exec`).
2. Визначте, хто в БД вчителі й кому належать дані:

   ```sql
   SELECT id, username, role FROM users WHERE role = 'TEACHER' ORDER BY id;
   SELECT count(*) FROM tests;  SELECT count(*) FROM quizlet_modules;
   SELECT count(*) FROM users WHERE role = 'STUDENT';
   ```
3. Задайте в `.env` `LEGACY_TEACHER_USERNAME` (за потреби `LEGACY_ASSIGN_ALL_STUDENTS=true`), `ADMIN_USERNAME`, `ADMIN_PASSWORD`.
4. `git pull && docker compose up -d --build`. Перевірте лог `backend`: рядки `Передано вчителю ...` і `Створено акаунт адміністратора ...`.
5. Якщо застосунок не стартував, прочитайте діагностику в логах, виправте `.env` і запустіть знову: міграції вже
   застосовані, дані не змінені.

## Відкат

Міграції адитивні, тому стару версію коду можна запустити на мігрованій БД (Flyway ігнорує невідомі «майбутні» версії).
Повний відкат даних: відновити `pre_stage2.dump` у порожню базу (`pg_restore`) і запустити попередню версію.

## Що змінилося у видимості даних

- Вчитель бачить, редагує й видаляє лише власні тести та модулі; системні (`owner_id IS NULL`) лише читає.
- Список учнів, результати, статистика, скидання пароля й видалення учня обмежені учнями цього вчителя (`users.teacher_id`).
  Спроби проходження тестів, зроблені акаунтами з роллю TEACHER, лишаються в БД і доступні їхньому власнику через «Мої результати».
- Нові учні, що реєструються за спільним кодом запрошення, прив'язуються до `LEGACY_TEACHER_USERNAME`
  (персональні коди вчителів: етап 3). Керувати спільним кодом може лише цей вчитель і адміністратор.
- Анонімні користувачі бачать лише системні матеріали.
- Зображення приватних матеріалів віддаються лише за підписаним посиланням (`?exp=...&sig=...`, HMAC-SHA256, строк дії перевіряється
  на сервері); системні зображення публічні.
- Підписки (`subscriptions`) лише зберігаються, доступ за ними **не обмежується** (до окремого рішення).
